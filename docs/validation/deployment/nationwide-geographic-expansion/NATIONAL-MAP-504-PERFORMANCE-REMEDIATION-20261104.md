# National map 504 performance remediation — 2026-11-04

## Result

`NATIONAL_MAP_504_REMEDIATION = COMPLETE`

The historical 504 was generated by Nginx after its 60-second upstream response-header wait expired. The old geography-summary handler performed one source-location membership query per current Master and recomputed geography readiness twice. A bounded direct baseline measured 6,667 SQL executions for 6,657 Masters. The fix batches these memberships into one distinct query and reuses the already-computed readiness value. No API fields, filters, counts, or membership semantics changed.

The old API container had already been replaced before this investigation. Nginx retained the error/access entries, but its access format did not retain request IDs or timing fields, and the original FastAPI logs and incident-time pool/CPU snapshots were unavailable. Therefore the 504-producing invocation’s exact FastAPI duration and incident-time resource state cannot be reconstructed. The code-level N+1, query counts, startup concurrency, and timeout evidence are directly confirmed; attributing the entire historical delay to one resource without those missing records would overstate the evidence.

## 504 evidence and request path

At `2026-11-04 12:15:34 UTC`, Nginx logged `upstream timed out ... while reading response header from upstream` for:

```text
GET /api/data-dashboard/geography-summary?
upstream: http://172.31.240.2:8000/api/data-dashboard/geography-summary?
```

The matching access entry returned `504` with a 569-byte Nginx error body and dashboard referrer. The API route had no explicit timeout; Nginx’s effective default `proxy_read_timeout` is 60 seconds. The `/api/` location did not override it. The configured 240-second timeout applies only to XLSX export. The access format does not include `$request_id`, `$request_time`, `$upstream_response_time`, or `$upstream_status`; the error/access records can be correlated by time, path, and dashboard referrer, not by a logged request ID.

The dashboard’s initial render loads the dashboard data, the national map endpoint, and the geography summary. The summary and map calls can overlap. The summary endpoint uses PostgreSQL through `SessionLocal`; it does not use Redis or a cache.

The API pool configuration is `pool_size=10`, `max_overflow=20`, `pool_timeout=30s`, with `pool_pre_ping`; the worker is configured for concurrency 4. Redis was healthy in the accepted local deployment but is not on this endpoint’s request path. The incident-era API container had been replaced, so historical pool checkout/overflow, API CPU/memory, and PostgreSQL activity snapshots were unavailable. The contemporaneous Nginx log also recorded the map response being buffered to a temporary file; this supports the concurrent-load context, but does not identify a separate database failure.

The replaced implementation queried source-linked geographic units inside the loop over every current Master. The national request returned 6,657 Masters and executed 6,667 statements, including 6,660 statements with the repeated geographic-unit query shape. It also called `_geographic_reference_readiness()` once directly and again through `_geographic_feature_state()`.

The sampled per-Master `EXPLAIN ANALYZE` used existing indexes and completed in 0.155 ms. Its plan scanned 41 `opportunity_locations` rows and used the existing `source_opportunities.master_opportunity_id` and geographic-unit primary-key indexes. This was repeated-query overhead, not evidence for a missing index. No index or schema change was made.

## Fix

In `app/main.py`, the summary handler now:

- derives feature state from its existing readiness result instead of reading readiness again;
- initializes each Master’s membership set from its direct geography unit;
- fetches all source-linked Master/unit pairs in one `SELECT DISTINCT` and unions them into those sets;
- preserves the existing unique-Master aggregation, response keys, filtering, coordinate verification, and empty-result behavior.

The 6,657-ID batch query plan completed in 0.378 ms execution time (4.426 ms planning). It returned the existing 12 distinct Master/unit pairs in the sampled plan. No speculative indexes, cache, stale-data behavior, centroid, canonical geography edit, or coordinate-provenance edit was introduced.
